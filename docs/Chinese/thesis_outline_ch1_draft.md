## 第一章 绪论（完整初稿）

### 1.1 研究背景与意义

随着居民健康意识不断增强，慢病管理、日常健康咨询、用药提醒和就诊后信息整理等需求日益增长。传统健康管理方式主要依赖线下咨询与人工记录，存在信息分散、反馈不及时、长期跟踪困难等问题。近年来，大语言模型技术在自然语言理解、知识问答和多轮对话方面取得了显著进展，使得“个人智能健康助手”成为可落地的应用方向。

然而，在真实健康场景中，仅依赖单一对话模型仍然存在明显局限：一方面，健康问题通常具有跨任务特征，涉及档案查询、报告解析、风险提示、提醒调度等多个子任务；另一方面，系统需要连接多类外部能力，如OCR识别、数据库查询、知识检索与任务编排，单体式架构容易出现模块耦合高、扩展成本大、维护困难的问题。

在此背景下，多智能体协同与工具化调用成为提升系统可用性和工程可持续性的关键路径。A2A机制强调智能体之间通过统一协议进行任务协作，适合将复杂健康服务拆解为多个具备明确职责的Agent；MCP机制强调工具能力标准化接入，为模型调用外部功能提供统一接口。二者结合能够在“任务分工”和“能力扩展”两个维度支撑智能健康助手系统构建。

本课题面向个人健康管理场景，设计并实现一个基于A2A-MCP的个人智能健康助手系统。系统围绕“健康咨询、健康档案管理、用药提醒、就诊摘要生成”四类核心功能进行构建，通过多智能体协作和工具编排完成端到端服务。该研究不仅具有较强的工程实践价值，也为多智能体架构在垂直健康场景中的落地提供了可复用参考。

本研究的意义主要体现在以下三个方面：

1. 理论与方法意义：将A2A协同思想与MCP工具协议结合，形成面向复杂健康任务的系统化设计方法。
2. 工程实现意义：通过模块化架构实现职责解耦，提升系统的可扩展性、可维护性与可演进能力。
3. 应用实践意义：围绕真实健康使用链路提供完整功能闭环，提升用户健康信息管理的便捷性和连续性。

### 1.2 国内外研究现状

在国际研究与产业实践中，智能健康助手经历了从“规则驱动问答”到“数据驱动对话系统”再到“大模型增强代理系统”的演进。早期系统通常依赖固定知识库和模板化问答，虽然在特定领域问题上可控性较高，但泛化能力不足。随着深度学习与预训练语言模型发展，系统在语义理解和自然语言生成方面得到明显提升，能够支持更自然的多轮交互。

近年来，国外在多智能体协同与工具调用方面研究持续增多。一类工作关注代理角色分工与任务分解，将复杂任务拆解后交由不同代理并行或串行执行；另一类工作关注函数调用与外部工具接入，通过统一接口实现数据库检索、代码执行、文档解析等能力扩展。这些方法在复杂场景中显著提升了系统任务完成率与可解释性。

国内相关研究与应用同样发展迅速，特别是在医疗健康、政务服务、企业客服等领域，出现了大量结合大模型的垂直系统。智能健康方向常见方案包括：医疗知识问答、体检报告解读、慢病随访提醒、电子病历信息抽取等。总体来看，国内研究在场景化落地与工程化部署方面推进较快，但在多智能体标准协同协议、工具接口统一规范、系统可扩展验证等方面仍有进一步提升空间。

综合现有研究可见，当前仍存在以下共性问题：

1. 单Agent架构在复杂业务下职责边界不清，易导致系统复杂度随功能增长迅速上升。
2. 工具接入方式缺乏统一标准，跨模块调用链路长、复用性不足。
3. 对系统级性能、稳定性与可扩展性评估不足，论文多聚焦算法效果而弱化工程验证。

因此，本课题以A2A-MCP为核心，强调“协议统一 + 模块解耦 + 工程验证”，在个人智能健康助手场景中提供一套从架构设计到系统实现再到测试评估的完整方案。

### 1.3 研究内容与技术路线

本课题的研究目标是设计并实现一个可落地的个人智能健康助手系统，满足健康咨询与信息管理场景下的多任务协同需求。围绕该目标，本文开展以下研究内容：

1. 构建多智能体协同架构。根据业务职责划分健康顾问、健康档案管理员、用药提醒助手、就诊摘要生成器等Agent，通过A2A协议实现任务消息互通和状态更新。
2. 构建统一工具调用机制。基于MCP协议封装OCR、数据库访问、知识检索等工具能力，实现Agent对外部功能的标准化调用。
3. 设计端到端任务链路。实现从用户请求接入、任务解析、流式响应、工具回调到结果汇总的完整流程，并支持消息和附件持久化。
4. 进行系统测试与评估。围绕功能正确性、性能表现、稳定性与可扩展性开展实验，验证方案有效性。

在技术实现层面，系统采用前后端分离和微服务化部署思路：后端使用Python及异步框架完成A2A服务与任务管理，前端提供消息交互与附件上传能力，数据库负责会话与业务数据持久化，SSE用于流式响应传输。系统通过Docker进行组件化部署，便于统一管理与复现实验环境。

本文技术路线可概括为：需求分析 → 架构设计 → 协议与模块实现 → 联调测试 → 结果评估与总结。具体过程包括：

1. 在需求阶段明确用户场景、功能边界和非功能指标；
2. 在设计阶段完成总体架构、模块职责和数据模型设计；
3. 在实现阶段完成A2A请求分发、任务管理、MCP工具调用、流式响应与持久化；
4. 在测试阶段完成功能用例、性能与稳定性测试，并进行结果分析。

### 1.4 主要贡献与创新点

相较于仅关注单点能力的智能问答系统，本文面向“系统级构建与落地”进行设计与实现，主要贡献如下：

1. 提出并实现了面向个人健康场景的A2A-MCP融合架构。该架构通过智能体分工与协议化工具接入，将复杂健康任务拆解为可协同、可扩展的执行单元。
2. 设计了流式任务处理与状态反馈机制。系统支持任务提交、处理中间状态回传、工具调用结果回灌与最终结果收敛，提升了交互实时性与链路透明度。

本文的创新点主要体现在以下两个层面：一是架构创新，即以A2A与MCP双协议协同解决多任务健康服务的系统复杂性；二是工程创新，即在统一任务链路中融合流式响应、工具回环和持久化机制，形成可复用的实践范式。

## 第二章 相关技术与理论基础（完整初稿）

### 2.1 A2A多智能体协同机制

A2A（Agent-to-Agent）是一种面向智能体协作的通信机制，其核心思想是将复杂任务拆分为多个职责明确的Agent，通过标准化消息协议完成任务分发、状态同步和结果汇聚。相较于单Agent串行处理方式，A2A机制能够在复杂业务场景中实现更清晰的职责边界和更高的系统扩展能力。

在个人健康助手场景中，用户请求往往跨越多个业务域。例如“我最近体检异常指标需要注意什么，并提醒我按时服药”这一需求，既涉及健康档案检索，又涉及医学解释与提醒调度。若由单一模块承载全部逻辑，系统容易形成高耦合。A2A架构通过角色分解将任务交由不同Agent处理，例如健康顾问Agent负责对话理解与综合输出，健康档案Agent负责病历与报告检索，用药提醒Agent负责周期任务编排，就诊摘要Agent负责结构化总结。各Agent聚焦本域能力，能够显著降低系统复杂性。

A2A机制通常包含以下关键能力：

1. 标准化能力发现：每个Agent对外暴露能力描述与可调用接口，便于其他Agent或网关进行动态路由。
2. 任务消息交互：通过统一请求结构传递任务上下文、用户输入和会话标识，实现跨Agent协作。
3. 状态可观测：支持任务处理中间状态与最终状态回传，提升可调试性与用户体验。
4. 协同可扩展：新增Agent主要通过能力注册与路由配置接入，通常无需改动任务主链路。

本课题采用A2A机制构建多智能体协同体系，重点解决两个问题：第一，复杂健康任务如何在多个Agent之间高效分工；第二，协同过程如何保持链路透明和状态一致。通过标准化任务协议与状态事件设计，系统能够在流式交互场景下持续反馈处理进度，并最终汇总多Agent结果返回用户。

### 2.2 MCP工具协议与调用机制

MCP（Model Context Protocol）用于规范模型与外部工具之间的调用方式，其目标是将“模型推理能力”和“系统执行能力”解耦。模型擅长语言理解与决策，而外部工具擅长执行确定性任务，如数据库检索、OCR识别、结构化计算和外部API访问。通过MCP统一接口，模型能够以可控方式调用工具，实现从“能回答”到“能执行”的能力升级。

在工程实践中，工具调用常见痛点包括接口不统一、参数格式不一致、错误处理分散和复用困难。MCP通过标准化工具描述、参数规范和调用返回结构，降低了工具接入复杂度，使不同能力可以以相同方式被Agent调度。对于本课题而言，这一点尤为关键：健康场景涉及OCR、知识检索、病历处理、提醒编排等异构能力，若无统一协议，系统维护成本将显著上升。

MCP调用流程可抽象为四个阶段：

1. 工具注册阶段：工具服务以统一格式暴露名称、参数与功能说明。
2. 工具选择阶段：Agent根据当前任务语义决定是否调用工具及调用何种工具。
3. 工具执行阶段：系统完成参数校验、远程调用与结果封装。
4. 结果回灌阶段：工具结果回写至对话上下文，供模型继续推理与生成。

在本系统中，检索增强生成（RAG）作为MCP工具层的重要能力落地。具体采用“向量召回 + 关键词兜底 + Rerank重排”的组合策略：先对查询进行向量检索获取候选片段，再在向量能力不可用或召回不足时回退关键词检索，最后通过重排模型提升候选相关性。该策略兼顾了语义匹配能力、可用性与工程稳定性，能够在健康咨询与档案问答场景下为主协调Agent提供更高质量上下文。

该机制使系统具备良好的可扩展性。新增工具时，开发者只需按照MCP规范注册，无需重构核心对话流程；替换工具实现时，只要接口契约稳定，上层Agent逻辑无需修改。基于这一优势，本课题将MCP作为工具层核心协议，用于支撑健康业务能力的持续迭代。

### 2.3 大语言模型与流式响应技术

大语言模型是智能健康助手的认知中枢，承担用户意图识别、上下文理解、答案组织与决策生成等关键任务。在医疗健康场景中，用户表达通常包含口语化描述、时序信息和隐含诉求，模型的语义理解能力直接影响交互质量。通过多轮上下文管理，系统能够维持会话一致性，提高回答的连贯性和针对性。

然而，仅有模型推理能力并不足以满足实时交互需求。传统“整包返回”模式需要等待完整生成后再展示，用户感知时延较高，且在调用外部工具时缺乏过程反馈。为此，系统引入流式响应机制，将生成内容按增量片段持续推送到前端，使用户在等待期间即可获取中间结果和状态更新。

本课题采用SSE（Server-Sent Events）承载流式输出，结合任务状态事件实现以下能力：

1. 增量文本传输：模型生成内容逐步到达前端，降低首字等待时间。
2. 处理中间可见：在工具调用与跨Agent协作阶段，前端可展示“处理中”状态。
3. 最终状态收敛：任务完成后统一返回终态标识，确保消息一致性与可追踪性。
4. 异常统一兜底：链路异常时返回规范化错误对象，避免前端状态失控。

流式机制不仅优化用户体验，也增强了系统可观测性。对于毕业设计这类工程项目而言，流式事件链路有助于在测试阶段定位瓶颈与异常点，为后续性能优化和稳定性改进提供基础。

### 2.4 OCR与医疗文本结构化技术

个人健康管理场景中的关键数据大量存在于非结构化文档中，如检验报告、处方单、出院小结和影像报告截图。若仅依赖用户手动录入，不仅成本高且容易出错。OCR（Optical Character Recognition）技术能够将图像或PDF中的文本内容提取为机器可处理数据，是健康档案数字化的重要基础能力。

医疗文档处理难点在于版式复杂、字段多样与术语密集。单纯文本提取往往不足以直接支撑下游问答和检索，必须进一步进行结构化处理。常见做法包括字段识别、实体归一化和标签映射。例如将“总胆固醇”“TC”统一映射为同一指标，将“参考范围”与“检测值”建立对应关系，从而支持后续异常判断和语义检索。

在本课题中，OCR与结构化流程主要包含以下步骤：

1. 文档接入：接收用户上传的图片或PDF并完成格式校验。
2. 文本识别：调用OCR服务提取文字内容与位置信息。
3. 信息抽取：识别关键医学字段，如项目名、数值、单位、参考区间、时间。
4. 数据清洗与存储：进行规范化处理后写入数据库或向量索引。
5. 业务消费：由健康档案Agent和健康顾问Agent在检索与问答中调用。

通过引入OCR与结构化能力，系统能够将离散的文档信息转化为可计算、可检索、可追溯的数据资产，从而提升健康咨询的准确性与上下文完整性。

### 2.5 本章小结

本章围绕系统实现所需的关键技术基础进行了阐述。首先，A2A多智能体协同机制为复杂健康任务提供了分工明确、可扩展的组织方式；其次，MCP工具协议为异构能力接入提供了统一调用规范，提升了系统复用性与可维护性；再次，大语言模型结合SSE流式响应技术，兼顾了语义理解能力与实时交互体验；最后，OCR与医疗文本结构化技术为健康档案数字化和下游智能服务提供了数据支撑。

上述技术共同构成本文后续系统设计与实现的理论和工程基础。下一章将基于这些技术，进一步开展系统需求分析，明确业务目标、功能边界与非功能指标，为总体架构设计提供依据。

## 第三章 系统需求分析（完整初稿）

### 3.1 业务场景分析

本系统面向个人健康管理场景，核心目标是通过智能化手段提升用户在“咨询、记录、提醒、复盘”四个环节的效率与体验。结合实际使用路径，系统主要服务于以下典型场景：

1. 日常健康咨询场景。用户通过自然语言提出健康相关问题，例如指标异常解释、饮食建议或症状咨询，系统需要在理解用户意图的基础上给出结构化、可读性强的回复。
2. 健康档案管理场景。用户上传体检报告、处方单、病历截图等资料，系统需要完成OCR识别、信息抽取与存储，为后续检索和问答提供数据支撑。
3. 用药提醒管理场景。用户根据处方信息配置提醒计划，系统需要支持定时提醒、状态更新与提醒历史追踪。
4. 就诊信息复盘场景。用户在就诊后希望快速生成摘要，系统需要对多源信息进行归纳，输出可复用的结构化总结。

从参与主体来看，系统包含用户、前端交互层、A2A智能体层、MCP工具层和数据层。用户通过前端发起请求；健康顾问Agent负责统一理解和编排；健康档案Agent、用药提醒Agent、就诊摘要Agent在各自职责域内完成子任务；MCP工具层提供OCR、检索和任务执行能力；数据层负责会话、消息、附件及业务数据持久化。

从业务闭环角度，本系统强调“输入可沉淀、过程可观测、结果可追溯”。输入可沉淀体现在文档上传后的结构化归档；过程可观测体现在流式响应与任务状态更新；结果可追溯体现在会话历史与任务状态事件。该闭环设计能够支持长期健康管理，而非一次性问答。

### 3.2 功能需求分析

结合课题目标与系统定位，本文将功能需求划分为用户交互功能、智能体协同功能、工具服务功能和数据管理功能四类。

1. 用户交互功能需求

- 支持文本问答、历史会话查看和多轮对话上下文保持。
- 支持附件上传，包括图片和PDF等常见健康文档格式。
- 支持流式结果展示，能够实时看到模型生成内容及处理中状态。
- 支持任务完成结果查看与历史消息回溯。

2. 智能体协同功能需求

- 支持健康顾问Agent作为主协调者对请求进行意图识别与任务分发。
- 支持健康档案Agent执行报告检索与内容归档相关任务。
- 支持用药提醒Agent完成提醒任务创建、查询和状态管理。
- 支持就诊摘要Agent对就诊信息进行提炼并输出结构化摘要。
- 支持跨Agent任务协同和统一结果汇总。

3. 工具服务功能需求

- 支持MCP统一工具注册与调用。
- 支持OCR识别工具，将附件内容转换为可处理文本。
- 支持知识检索和数据库查询工具，为咨询与总结提供事实支撑。
- 支持工具执行结果回灌到对话上下文，形成可持续推理链路。

4. 数据管理功能需求

- 支持用户会话与消息记录持久化，并支持任务状态的内存态跟踪。
- 支持附件元数据和解析结果存储。
- 支持健康档案的基础检索与按时间维度查询。
- 支持提醒任务的状态更新和历史记录。

为了保证功能完整性，系统需要满足“请求接入—任务执行—状态反馈—结果回传—数据沉淀”的全链路闭环要求。任何核心功能都应能在该链路中找到明确位置，以保证后续设计与实现的一致性。

### 3.3 非功能需求分析

除功能正确性外，个人智能健康助手作为长期使用系统，还需要满足性能、稳定性、安全性和可扩展性等非功能要求。

1. 性能需求

- 接口首响应时间应尽量缩短，支持流式输出降低用户等待感知。
- 常规咨询请求在可接受时间内返回完整结果，避免长时间阻塞。
- 系统应支持并发请求场景，保证核心链路稳定运行。

2. 稳定性需求

- 系统在工具调用失败、网络抖动等异常场景下应具备兜底处理能力。
- 任务状态应具备一致性，避免出现前端显示与后端状态不一致。
- 对关键流程应有可观测日志，便于定位问题与快速恢复。

3. 安全性需求

- 用户数据和健康信息应避免明文暴露，敏感字段应进行必要保护。
- 接口调用应具备基础访问控制与输入校验，防止非法请求注入。
- 文件上传应进行格式与大小校验，防止异常文件影响系统运行。

4. 可扩展性需求

- 新增Agent时不应破坏已有交互协议和主流程。
- 新增工具时应通过统一MCP规范接入，减少改动范围。
- 架构应支持后续扩展多用户隔离、监控告警和更复杂业务编排。

5. 可维护性需求

- 模块职责应清晰，接口边界明确，减少耦合。
- 配置应集中管理，便于部署环境迁移和参数调整。
- 关键流程应具备文档化说明，支持团队协作开发。

综上，非功能需求不仅影响系统体验，也直接决定毕业设计的工程质量与可复现性，是后续系统设计必须重点落实的部分。

### 3.4 用例与流程分析

为将需求转化为可实现的设计，本节采用典型用例描述系统核心流程。

1. 用例一：健康咨询与档案联动问答

- 参与者：用户、健康顾问Agent、健康档案Agent、检索工具。
- 前置条件：用户已创建会话，系统可访问健康档案数据。
- 基本流程：用户提出咨询问题；健康顾问Agent识别需要档案信息；触发健康档案Agent检索相关记录；系统汇总检索结果并生成回答；前端流式展示并保存会话。
- 后置条件：本次问答结果与引用信息写入会话历史。

2. 用例二：体检报告上传与结构化入库

- 参与者：用户、前端上传模块、OCR工具、健康档案Agent、数据库。
- 前置条件：用户完成登录或身份识别，上传文件符合格式要求。
- 基本流程：用户上传报告；系统进行文件校验；调用OCR识别文本；抽取关键指标并规范化；入库并建立检索索引；返回处理结果。
- 后置条件：用户可在后续咨询中直接引用该报告信息。

3. 用例三：用药提醒创建与执行

- 参与者：用户、健康顾问Agent、用药提醒Agent、提醒调度服务。
- 前置条件：用户提供药品、频次和时间等必要信息。
- 基本流程：系统解析提醒意图；创建提醒计划；写入任务记录；到达触发时间执行提醒；记录执行状态并反馈给用户。
- 后置条件：提醒任务可查询、可更新、可终止。

4. 用例四：就诊摘要生成

- 参与者：用户、健康顾问Agent、就诊摘要Agent、档案数据源。
- 前置条件：存在可用于总结的就诊记录或上传资料。
- 基本流程：用户发起摘要请求；系统聚合相关资料；就诊摘要Agent生成结构化摘要；用户查看并可二次追问。
- 后置条件：摘要结果归档到会话与档案系统。

在流程层面，系统统一采用“请求接入—任务管理—Agent协同—工具执行—流式回传—结果持久化”模型。该流程既适用于单一问答，也适用于跨Agent协同任务，有利于后续架构统一实现。

## 第四章 系统总体设计（完整初稿）

### 4.1 系统总体架构设计

基于第三章需求分析结果，系统总体设计遵循“分层解耦、协议统一、链路可观测、能力可扩展”的原则。整体上采用前后端分离与多服务协同架构，由接入层、A2A智能体层、MCP工具层和数据层构成。

1. 接入层负责用户请求承接与交互呈现。前端提供文本对话、附件上传、流式展示和历史会话管理能力；后端网关负责请求路由、参数校验和统一响应封装。
2. A2A智能体层负责业务理解与任务编排。健康顾问Agent作为主协调者，对用户意图进行识别并决定是否调用其他Agent完成子任务。
3. MCP工具层负责外部能力执行。OCR、检索、数据库访问和任务调度能力通过统一工具协议暴露，供各Agent按需调用。
4. 数据层负责业务数据持久化，包括会话消息、附件元数据和结构化健康档案；任务状态由任务管理模块在内存中维护。

该架构通过职责隔离避免了单体系统中常见的逻辑堆叠问题，使“对话理解”“工具执行”“数据持久化”分别在独立模块中演进。对毕业设计而言，这种架构不仅便于展示系统设计合理性，也更利于后续迭代与复现实验。

### 4.2 智能体模块划分与职责

为满足健康场景下多任务协同需求，系统将Agent按业务职责拆分为四类核心角色：

1. 健康顾问Agent

- 作为主入口处理用户自然语言请求。
- 负责意图识别、上下文管理与任务调度决策。
- 在需要专业子能力时调用其他Agent或工具，并汇总最终回复。

2. 健康档案Agent

- 负责健康资料检索、文档解析结果管理与档案查询。
- 对接OCR结果与结构化数据，为问答和总结提供事实依据。
- 支持按时间、指标、报告类型等维度进行信息提取。

3. 用药提醒Agent

- 负责提醒任务创建、更新、终止与状态追踪。
- 管理提醒规则，如频次、时段、持续周期等业务参数。
- 输出提醒执行结果并回写任务记录。

4. 就诊摘要Agent

- 负责对就诊相关材料进行归纳和摘要生成。
- 输出结构化总结内容，支持用户复盘与二次追问。

该划分方式的核心价值在于“高内聚、低耦合”。各Agent关注本域能力，避免跨域逻辑混杂；当新增业务能力时，可通过新增或扩展Agent实现最小改动接入。

### 4.3 A2A任务交互设计

系统采用统一任务消息模型实现A2A交互，核心流程包括任务创建、任务执行、状态更新与结果回传四个阶段。对外接口支持普通请求与流式订阅请求，其中流式链路用于提升交互实时性。

1. 任务创建阶段

- 接入层接收用户请求并生成任务标识。
- 绑定会话上下文、用户输入和附件引用信息。
- 写入任务初始状态，进入执行队列。

2. 任务执行阶段

- 健康顾问Agent解析意图并决定执行路径。
- 若请求涉及子域能力，则通过A2A方式触发目标Agent处理。
- 目标Agent可继续调用MCP工具完成具体操作。

3. 状态更新阶段

- 系统在关键节点回传处理中状态，包含开始执行、工具调用、等待结果、完成等。
- 流式事件用于将中间进展实时推送给前端，提升透明度。

4. 结果回传阶段

- 子任务结果由协调Agent汇总并生成最终回复。
- 任务状态更新为完成或失败，并记录异常信息（如有）。
- 对话消息与任务记录同步持久化，支持后续回溯。

通过该交互设计，系统实现了从请求到响应的全链路可追踪机制，确保多Agent协同过程可观测、可调试、可复盘。

### 4.4 MCP工具层设计

工具层采用MCP协议统一管理工具注册、调用、返回与错误处理。其设计目标是在不改变上层Agent逻辑的前提下，支持工具能力的灵活扩展。

1. 工具注册机制

- 每个工具以标准描述暴露能力名称、参数定义与返回结构。
- Agent在运行时可基于工具描述进行自动选择和调用。

2. 调用执行机制

- Agent发起调用请求后，工具层完成参数校验与路由执行。
- 工具执行结果以统一结构返回，便于上层消费与二次推理。

3. 异常处理机制

- 工具执行失败时返回标准化错误对象，避免异常泄漏。
- 错误信息可被任务管理模块记录，用于后续定位和恢复。

4. 扩展接入机制

- 新增工具只需按MCP契约注册，无需改造任务主流程。
- 工具替换或升级可在协议稳定前提下平滑完成。

本设计使工具层成为稳定的能力基座。无论是OCR能力增强，还是新增医学知识检索能力，都可在保持系统整体结构稳定的前提下快速落地。

围绕知识检索能力，工具层进一步形成了标准化RAG链路：文档入库阶段完成分块、向量化与索引写入；在线查询阶段执行向量召回与重排；回退路径采用关键词检索保障可用性。该链路通过统一契约暴露给Agent调用，使“知识增强回答”与“普通工具调用”在工程上具备一致的调用与回灌模型。

### 4.5 数据模型与数据库设计

为支撑会话交互、任务管理和健康资料沉淀，系统设计了面向业务的核心数据对象，包括用户会话、消息记录、任务记录、附件信息和结构化档案。

1. 会话与消息模型

- 会话模型用于组织多轮对话上下文，记录会话标识、用户标识、创建时间等。
- 消息模型记录用户输入、系统回复、消息类型和时间戳，支持历史追溯。

2. 任务模型

- 任务模型记录任务标识、任务状态、处理节点、关联会话与错误信息。
- 支持状态流转管理，用于追踪任务生命周期和排障分析。

3. 附件与解析模型

- 附件模型记录文件路径、类型、上传时间和关联消息。
- 解析模型保存OCR文本、结构化字段与校验结果，供后续检索使用。

4. 健康档案模型

- 以用户维度管理健康指标、报告摘要、就诊记录等信息。
- 支持按时间、类别和关键词检索，服务健康咨询与总结任务。

数据库设计强调“一致性与可追溯”。关键对象均保留必要时间字段和关联键，确保系统能够对任一结果追踪到源输入、处理过程和最终输出。

### 4.6 安全与异常处理机制

医疗健康数据具有敏感性，因此系统在总体设计阶段即纳入安全与异常处理要求，重点覆盖访问控制、输入校验、数据保护和链路兜底四个方面。

1. 访问控制与鉴权

- 对外接口设置基础身份识别与访问控制策略。
- 对关键写操作进行权限约束，避免未授权调用。

2. 输入与文件校验

- 对文本输入进行长度与格式约束，防止异常请求影响服务。
- 对上传文件进行类型、大小与内容校验，降低恶意文件风险。

3. 数据保护策略

- 避免在日志中输出完整敏感信息，必要时进行脱敏处理。
- 对核心数据访问路径进行隔离，减少越权读取风险。

4. 异常兜底与恢复

- 在任务执行链路中统一捕获异常并返回标准化错误响应。
- 记录关键异常上下文，便于后续排查和修复。
- 保证异常场景下任务状态可终止并返回规范错误，避免状态悬挂。

通过安全与异常机制的前置设计，系统能够在保证业务连续性的同时降低健康数据处理风险，为工程化落地提供基本保障。

## 第五章 系统详细实现（完整初稿）

### 5.1 服务端请求分发与任务管理实现

系统后端以统一服务入口承接前端请求，并通过任务管理模块驱动后续执行链路。实现上采用“请求解析—任务创建—执行调度—状态回传—结果持久化”的顺序处理模型，以保证复杂请求在多模块协同下仍具备一致性与可追踪性。

在请求分发阶段，服务端首先完成请求体解析、参数校验和会话上下文绑定。对于普通问答请求，系统直接进入任务执行流程；对于流式订阅请求，系统在创建任务后进入增量事件推送模式。该设计使同步与流式链路共用同一任务内核，降低了维护复杂度。

任务管理模块承担以下职责：

1. 任务生命周期管理：创建任务、更新状态、标记完成或失败。
2. 会话关联管理：将任务与会话、用户、消息记录关联，保证链路可追溯。
3. 执行调度管理：调用主协调Agent并接收中间事件与最终结果。
4. 异常统一处理：捕获链路异常并转换为规范化错误响应。

在工程实现中，任务管理采用状态机思想控制状态流转，典型状态包括“submitted、working、input-required、completed、failed、canceled”。每个状态变化都会触发记录更新，为测试阶段的问题复盘提供依据。

### 5.2 Agent推理与工具回环实现

系统将健康顾问Agent作为主协调者，通过“推理—决策—调用—回灌—再推理”的回环机制完成复杂请求处理。该机制是多智能体系统从“被动回答”走向“主动执行”的关键实现路径。

实现流程如下：

1. 上下文构建：收集当前用户输入、历史消息、附件摘要和任务元信息，形成推理上下文。
2. 意图判定：主协调Agent识别请求属于咨询、档案查询、提醒管理或摘要生成等类型。
3. 执行决策：若仅需语言生成则直接回答；若需外部能力则触发工具调用或子Agent协作。
4. 结果回灌：将工具返回数据写回上下文，驱动下一轮推理。
5. 答案收敛：在满足完成条件后输出最终回复并返回任务终态。

为避免回环失控，系统设置了最大调用轮次、超时约束和异常短路策略。当工具连续失败或上下文无法收敛时，系统会触发降级回复并终止任务，保证服务可用性。

此外，系统保留了推理过程中的关键事件标记，如“调用了哪个工具”“工具是否成功”“是否触发重试”，这些信息可用于后续评估Agent决策质量和系统稳定性。

在知识密集型问答场景中，回环机制会显式触发RAG检索流程：先生成查询并调用检索工具，获取候选片段后拼接到上下文，再由主协调Agent完成证据驱动回答。当向量检索不可用或召回为空时，系统会自动切换到关键词检索路径；若候选较多则执行重排后截断返回，兼顾准确性与时延表现。

### 5.3 OCR识别与附件处理实现

附件处理模块负责将用户上传的健康文档转化为可检索、可计算的数据。实现上采用“上传接入—文件校验—OCR识别—结构化抽取—结果入库”的流水线方案。

1. 上传接入

- 前端提交文件后，后端首先校验文件类型、大小和完整性。
- 系统生成附件标识并建立与会话消息的关联关系。

2. OCR识别

- 调用OCR服务对图片或PDF进行文本识别。
- 识别结果包含原始文本与基础位置信息，用于后续字段抽取。

3. 结构化抽取

- 根据健康场景规则提取关键字段，如指标名、检测值、单位、参考区间、日期。
- 对同义字段进行统一映射，减少后续检索歧义。

4. 结果入库与复用

- 将附件元数据、OCR文本和结构化结果写入存储层。
- 在后续问答和摘要任务中按需检索，避免重复识别。

该实现的核心价值在于把一次上传沉淀为长期可复用数据资产，显著提升后续交互效率与回答准确性。

### 5.4 消息与附件持久化实现

系统采用统一持久化策略管理会话、消息和附件数据，并由任务管理模块维护任务状态，确保任何一次交互均可回溯其输入、处理过程与输出结果。为实现这一目标，后端在关键节点执行数据库写入与状态更新。

1. 消息持久化

- 用户输入、系统回复和中间事件均按时间顺序记录。
- 每条消息附带会话标识和消息类型，支持历史检索与重放分析。

2. 任务状态管理

- 任务创建后先进入submitted状态，执行过程中更新为working、input-required等状态。
- 任务完成或异常时收敛到completed或failed等终态，并通过流式事件回传给前端。

3. 附件持久化

- 保存附件路径、文件属性、关联消息与解析状态。
- OCR与结构化结果分层存储，支持按需查询与更新。

4. 一致性保障

- 关键写操作采用一致性控制，避免“消息已返回但任务未落库”等不一致问题。
- 异常路径下执行兜底写入，保证失败信息可追踪。

通过上述机制，系统实现了“对话可回看、任务可复盘、附件可复用”的数据闭环，为第六章测试分析提供可靠数据来源。

### 5.5 前端交互与流式展示实现

前端以聊天式交互为核心，围绕“输入便捷、反馈及时、状态透明”三个目标进行实现。页面支持文本输入、附件上传、历史会话查看和流式结果展示。

在交互流程上，前端先提交请求并立即展示占位状态；后端开始流式返回后，前端逐块拼接内容并实时渲染。对于工具调用或跨Agent处理阶段，前端通过任务状态事件展示“处理中”提示，减少用户等待焦虑。

具体实现要点如下：

1. 会话管理：支持会话创建、切换和历史记录加载，保证多轮上下文连续。
2. 流式渲染：按事件顺序增量更新回答内容，提升首字响应体验。
3. 附件交互：支持上传进度反馈与解析结果展示，增强用户可感知性。
4. 容错提示：当请求失败或超时时给出明确提示，并支持用户重试。

该前端实现与后端任务链路保持同构设计，即同样围绕任务状态驱动界面变化，从而保证系统整体交互一致性。

### 5.6 关键问题与解决方案

在系统实现过程中，主要遇到以下工程性问题，并通过针对性方案进行了处理。

1. 问题一：多Agent链路复杂，故障定位困难
   解决方案：为任务全链路增加状态节点与日志标识，统一记录任务ID与会话ID，实现跨模块追踪。

2. 问题二：工具调用结果不稳定，影响回答收敛
   解决方案：增加调用超时、重试与降级策略；对失败工具返回结构化错误，避免推理链路中断。

3. 问题三：流式返回中断导致前端状态错乱
   解决方案：在任务管理层统一定义终态事件；前端以终态作为渲染收敛条件，避免半完成状态悬挂。

4. 问题四：附件处理耗时长，影响交互体验
   解决方案：将上传确认与解析结果解耦，先反馈接收成功，再异步推进识别并通过状态更新提示进度。

5. 问题五：多类数据写入存在一致性风险
   解决方案：对关键写路径采用一致性控制与异常补偿，确保任务、消息和附件之间关联完整。

通过上述方案，系统在可用性、稳定性与可维护性方面得到明显提升，满足毕业设计工程实现要求。

## Abstract (Draft)

With the growing demand for personal health management, traditional service models based on manual recording and passive consultation show clear limitations in information integration, long-term tracking, and interactive experience. Although large language models provide new opportunities for intelligent health services, single-agent solutions still face challenges in complex task decomposition, external capability integration, and system scalability. To address these issues, this thesis proposes and implements a personal intelligent health assistant system based on A2A-MCP.

The system is designed around four core scenarios: health consultation, health record management, medication reminder, and visit summary generation. A layered architecture is adopted, including an access layer, an A2A agent collaboration layer, an MCP tool layer, and a data layer. A2A is used to support multi-agent task collaboration and status feedback, while MCP enables standardized registration and invocation of external tools such as OCR and retrieval services. A streaming interaction mechanism is introduced to improve first-response experience and enhance process observability. In addition, a complete persistence loop is implemented for sessions, messages, tasks, and attachments to support traceability and continuous reuse.

After implementation, the system is evaluated from four perspectives: functionality, performance, stability, and scalability. Experimental results show that the proposed system can stably complete core business workflows, provide good interactive experience in typical scenarios, and maintain engineering-level extensibility. Validation with newly added agents and tools further demonstrates the adaptability of the architecture. This work provides a practical and reusable reference for applying multi-agent systems to personal health management.
