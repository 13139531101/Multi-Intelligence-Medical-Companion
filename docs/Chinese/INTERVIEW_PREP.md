## 3. 技术难点深挖（主战场）

19 个故事，每个四段式：**现象 → 根因 → 修法 → 为什么难发现**。

故事 1-9 偏"功能怎么跑通"，故事 10-14 偏"怎么发现与度量"，**故事 15-19 偏"实现了却没生效"** —— 这一类最能体现**验证习惯**，也最容易被面试官追问"你怎么确认它真的在工作"。

### 故事 1：OCR 工具「碰巧能用」了 40 个阶段

**现象**：PhaCore 的 OCR 工具一直能调，没人报过错。

**根因**：三层套娃。

1. `mcp_tool_adapter.py` 里 `_list_phacore_tool_names` 调用了 `_extract_mcp_tools_from_source` —— **这个函数从来没被 import 进来**，调用必然抛 `NameError`。
2. 这个 `NameError` 被一个**裸 `except Exception`** 吞掉。
3. 于是它静默回退到一份**硬编码的 OCR-only 工具名列表**。

而当时的 PhaCore 恰好**只有 OCR 两个工具** —— 硬编码列表和真实列表**内容完全一致**。所以功能"正常"，直到我往 PhaCore 加了新工具，它们才会**凭空消失**。

**修法**：补上 import；把裸 `except` 改成 `except Exception as e` + `logger.warning`，让异常留下痕迹。

**为什么难发现**：因为**回退值恰好是对的**。这不是"代码有 bug 但没人测到"，而是"代码有 bug，且这个 bug 在当前数据下**不产生任何可观测差异**"。只有当你改变数据（加工具）时它才现形。

> 这类 bug 的通用形态是：**`except` 吞掉异常 + 回退到一个当前恰好正确的默认值**。它比崩溃危险得多，因为它会静默地把"未来"变成"不生效"。

### 故事 2：PhaCore 工具对模型是「不可调用」的

**现象**：工具加载成功、名字也在，但模型**从来不调它们**。

**根因**：包装器把函数包成了 `def wrapped(**kwargs)`。LangChain 只能从签名推出一个**不透明的 `kwargs` 参数** —— 模型在工具描述里看不到任何真实参数名（`category`、`message`、`image_base64` 全没了），等于给了模型一个没有说明书的按钮。

**修法**：改用同文件里**早就写好、只是没被调用**的 `_wrap_function_as_base_tool` —— 它用 `inspect.signature` 建真实的 pydantic `args_schema`，并调 `register_tool_sig()` 让参数注入逻辑能正确工作。它失败时返回 `None`，所以调用点要判空后 `continue`。

**验证方式**：跑起来打印每个工具的 `args_schema.model_fields`，要求 `filter_health_records → ['category']`，而不是空的或 `kwargs`。**这条断言直接验证了修复**。

**为什么难发现**：因为**不报错**。工具在列表里、schema 是合法的（`kwargs` 也是合法 schema）、调用链不抛异常 —— 唯一的表现是"模型不太聪明"。很容易被归因成"提示词没写好"。

> 教训：**"模型不调工具"要先怀疑工具描述，再怀疑模型。**

### 故事 3：`done` 之后还有事件，一 break 就丢

**现象**：AI 回答正确，但**页面不动**。

**根因**：bridge 是**先发 `done`、再发 `page_update`** 的。前端消费 SSE 时习惯性地在 `done` 上 `break` 退出循环 —— 于是尾部的页面动作**全部丢失**。

**修法**：`done` 不 break，继续读到流真正结束（由 `finish()` 兜底）。

**为什么难发现**：因为**它看起来完全符合直觉**。"done 就是结束了"是几乎所有人的第一反应。要发现它，必须知道后端的事件顺序 —— 而这个顺序在代码里没有任何强制约束，纯靠约定。

> 这条的通用教训：**"结束"事件不等于"最后一个"事件。** 事件流一旦有"结束标记 + 尾部动作"的结构，消费方就必须读到 EOF 而不是读到标记。

### 故事 4：401 变成了「一句错误都没有的空回复」

**现象**：token 过期时，用户看到一个转圈然后什么都没有 —— 没有报错、没有提示。

**根因**：转译层调用上游时**没有检查 HTTP 状态码**。上游返回 401，响应体是错误 JSON 而不是 SSE 流，转译层按 SSE 解析 → 解析不出任何事件 → 生成一个**空的事件流** → 前端认为"流正常结束了，只是没内容"。

**修法**：显式检查状态码，非 2xx 时生成一个 AG-UI `RUN_ERROR` 事件，把上游错误信息透出去。`tests/e2e/agui_smoke.py` 的路径 B 专门守这条：**无 token 时必须拿到 `RUN_ERROR`，而不是空回复**。

**为什么难发现**：因为**失败被伪装成了成功**。空流是一个合法的成功响应。这个 bug 只有在"认证过期"这种低频场景下才出现，而且表现出来像前端 bug。

> 教训：**任何"解析流"的地方，都必须先确认对方真的给了你一个流。**

### 故事 5：两套 RAG 共用一张表，余弦相似度被混算

**现象**：检索结果"感觉不太准"，没有报错。

**根因**：`rag_chunks` 表被**两套 RAG 栈共用** —— v2 主链路用 DashScope `text-embedding-v4`（384 维），HealthAdvisor 用 `all-MiniLM-L6-v2`。v2 的检索 SQL **没有按 `embedding_model` 过滤**，于是两套向量空间被混在一起算余弦相似度。

**修法**：检索 SQL 加 `embedding_model` 过滤（`rag.py:360-364`）。

**为什么难发现**：**维度相同或做了补齐时，SQL 不会报错。** 两个不同模型的向量在数值上都是合法的浮点数组，余弦相似度算得出来 —— 只是**没有意义**。表现是"检索质量下降"，而没有人会为一个"感觉有点不准"报警。

> 教训：**共享存储 + 多生产者时，必须有一个"命名空间列"。** 这是数据层的隔离问题，不是算法问题。

### 故事 6：知识图谱三张表永远是空的

**现象**：图扩展功能"实现了"，但检索结果里从来看不到图扩展带来的片段。

**根因**：写入函数 `index_document_with_kg` **没有任何调用方**。所以 `kg_entities` / `kg_relations` / `kg_entity_chunks` 三张表**永远空**，图扩展是个**静默的空操作** —— 代码全对、逻辑全通、结果永远是"没有可扩展的实体"。

**修法**：在文档入库管线里接上调用（阶段 48-p3）。

**为什么难发现**：**空表上的查询是成功的。** `SELECT ... FROM kg_entities WHERE ...` 返回 0 行不报错，BFS 遍历空图也不报错。整个链路的每一步都"成功"，合起来是"什么都没做"。

> 教训：**死代码有两种。一种是没人调的函数，一种是有人调但没人写的表。** 后者的隐蔽性高一个量级。

### 故事 7：RAG 改造在真正的产品链路上一次都没跑过

**现象**：`/metrics` 上 rerank 和 CRAG 的指标**恒为空**。

**根因**：系统有**两条并行路径**：

- `v2_process_message`（非流式）—— 走 `host_graph`，里面有 `rag_retrieve` / `crag_correct` / `critique`
- `v2_process_message_stream`（**流式，也就是产品实际走的**）—— **从不调用 `host_graph`**，自己做路由后直接 `agent.stream()`

P3 阶段的全部 RAG 改造都做在 host_graph 里。**结果：产品链路上一次都没执行过。**

**修法**：在流式路径里补上"检索 → CRAG 决策 → 注入 context"，并与 host_graph 的 `invoke_agent_node` **保持同样的注入格式**，保证两条路径拿到一致的上下文。整段失败降级为"无检索"，绝不打断对话。

**为什么难发现**：因为**代码是对的、功能是存在的、单测是能过的** —— 只是**装错了地方**。而且当时指标为空被解释成"没流量"，而不是"没接上"。

> 这是我最有感触的一条：**发现它的方式不是读代码，而是问"这个指标为什么是 0"。** 可观测性不只是排障工具，它是**发现"功能没接上"的唯一手段**。

### 故事 8：AST 扫描看不见 `async def`

**现象**：新写的 MCP 工具在发现列表里**不存在**，但不报错。

**根因**：工具发现用 **AST 静态扫描**（不 import、不执行用户代码 —— 这是为了安全和速度）。扫描器里写的是 `if not isinstance(node, ast.FunctionDef): continue` —— 只认同步函数，**`AsyncFunctionDef` 直接被跳过**。

**修法**：把所有 PhaCore 工具写成**同步 `def`**，并把这条约束写进模块 docstring。

**为什么难发现**：因为**写 `async def` 是更自然的选择**（尤其在其他工具都是 async 的情况下），而失败形式是"工具不存在"而非"工具报错"。

> 教训：**静态扫描器有它自己的"语言子集"。** 用静态分析替代运行时反射，换来的是安全与速度，代价是**你必须知道这个子集有多大**，并且把它写在显眼的地方。

### 故事 9：重排让 MRR 从 0.6167 提到 1.0

**现象**：向量检索的排序不够好，正确答案常常不在第一位。

**做法**：接入 DashScope 的 `gte-rerank-v2` HTTP 重排。

**关键设计**：

- **不部署本地模型**（项目硬约束）—— 走 HTTP API，不引入 cross-encoder，避免拖慢镜像、吃内存
- **任何失败都返回 `None`，调用方保留原始向量顺序** —— 只记 Prometheus 指标，**绝不抛异常**。重排是"锦上添花"，不能让它的故障升级成"检索失败"
- 8 秒超时

**结果**：**MRR 0.6167 → 1.0**。

**面试加分点**：主动说明"这是个只有 20 来条测试样本的小评测，1.0 说明的是**方向正确**，不是"生产级效果"。**主动给数字加边界，比给一个漂亮数字更可信。**

### 故事 10：一个被「测量」否掉的优化（负结果）

**想法**：rerank 已经算出了相关性分数，能不能用它**短路**掉 `evaluate_chunks` 那次 LLM 调用？省一次 LLM，省钱又提速。

**做法**：先去量两者的量纲。

**结果**：

- `gte-rerank-v2` 的 `relevance_score` 实际落在 **0.16 – 0.35**
- LLM 的相关性判断落在 **0.95** 附近

**两者是不同的量纲**，找不到任何一个阈值能同时做到"可靠触发"和"不误判"。**优化被否掉。**

**为什么值得讲**：因为**"想到 → 试了 → 用数据否掉"比"想到 → 做了 → 上线"更能体现工程判断**。而且它证明我有"先量再改"的习惯，而不是拍脑袋调参。

> 面试时这句可以直接说：**"这个优化我没做，因为量完发现两个分数不是一个量纲。"**

### 故事 11：`CurrentPage/refresh` 不能和 `navigateTo` 同批下发

**现象**（推演出来的，没等它上线）：用户说"刷新一下"，结果**刷的是上一个页面**。

**根因**：`navigateTo` 和 `refresh` 如果放在同一个 `actions[]` 里，会在**同一个 tick 派发**。此刻 `navigate()` 只是排了一个 state 更新，**旧页面还挂着** —— refresh 就打在了旧页面上。

**修法**：`refresh_current_page` **只发一个动作、不导航**。同时用「`CurrentPage` 模式」解决"后端怎么知道用户在哪一页"：**四个页面都注册同一个 `CurrentPage` 名字、只暴露 `refresh`**，后端无脑发 `CurrentPage/refresh` 就能命中当前页。因为总有页面挂载着，这条指令**永远走立即执行、不进队列**。

**为什么难发现**：**它是个时序竞态，且窗口极窄。** 而且它是"偶尔刷错页"，很容易被当成偶发 bug 忽略。

> 这条约束写进了代码注释 —— **约束如果不写下来，下一个人（或半年后的我）一定会再犯。**

### 故事 12：CI 守卫「从来没跑过」

**现象**：`tests/test_tool_dedup.py` 的 docstring 写着"失败禁止 merge"。

**根因**：三重失效，叠加起来等于零。

1. 它 import 的是 `A2AServer.v2.mcp_discover` —— **这个模块早就搬到 `A2AServer.mcp.mcp_discover`** 了，import 直接报错
2. 文件里**没有任何 `test_*` 函数** —— `pytest` 收集到 0 个测试，**退出码 5**
3. 它**根本没进 CI 流水线**

**修法**：修 import 路径；重写判据并补上 `test_no_tool_name_collisions()`；**接进 CI 并设为阻断**（`continue-on-error: false`）。

**顺便改了判据**：原版把 4 个 agent 的工具放进一个全局列表比对，**必然报 3 个"重复"**。但那 3 个是各 agent 的**私有工具**，而工具发现是**按 agent 隔离加载**的（没有任何全局聚合）—— 也就是说这 3 个"重复"**在运行时永远不可能冲突**。改成三条真实判据：

1. 单个 agent 内部无重名
2. PhaCore 内部无重名
3. PhaCore 名字不与任何 agent 的领域工具重名

**跨 agent 重名降级为 WARN。**

**为什么难发现**：因为**"测试文件存在"和"测试在跑"是两回事**。一个不跑的守卫比没有守卫更危险 —— 它给人虚假的安全感。

> 这条特别适合回答"你怎么保证质量"这类问题：**先确认守卫真的在跑，再谈守卫守得对不对。**

### 故事 13：浮窗没有多轮记忆（已实测定位）

**现象**：用户说"记住我叫张三"，下一句问"我叫什么"，AI 答"**没有可用的信息**"。

**根因**：浮窗（唯一支持页面操控的聊天入口）发请求时**只发 `{message}`，不带 `conversation_id`**。后端于是每轮生成一个新的 `stream_<8位随机>` 当会话 id，而它正是 LangGraph 的 `thread_id`。**每一句话都是一个全新的会话。**

**实测证据**（两轮 `conversation_id` 分别是 `stream_1153efdb`、`stream_9a3ee8fb`）：

| 场景 | 结果 |
|---|---|
| 不带 `conversation_id` | A1"我叫张三" → A2"我叫什么" → **答"没有可用的信息"** |
| 带同一个 `conversation_id` | B1"我叫李四，41岁" → B2"我叫什么" → **正确答"李四，41岁"** |

**结论**：**记忆能力本身是好的，只是浮窗没把会话 id 传下去。** 修复面是前端一行 + 会话级 id。

**为什么难发现**：因为**"没有记忆"看起来像模型能力问题**，而不是参数传递问题。而且另一个聊天入口（全页 `NewChat.jsx`）**是传了的** —— 所以"系统有没有记忆"这个问题，取决于你从哪个入口问。

> 顺带一提：这个 bug 的排查过程本身就是个好故事 —— **我没有改任何代码就定位了根因，靠的是构造对照实验（带 id / 不带 id）**。

### 故事 14：23/26 条档案落进了一个不存在的 tab

**现象**：档案页点任何分类 tab 都是空的。

**根因**：**两套词表**。数据库里 `record_type` 实际是 `other(8) / lab_report(5) / medical_report(5) / symptom(5) / allergy(3)`，而前端 `API_TO_TYPE` 只认 `diagnosis / examination / exam / report / allergy / medication`。

结果 **23/26 条映射失败落到 `other`，而 `other` 根本不是 `CATEGORIES` 的 key** —— 点哪个 tab 都筛不出东西。

**修法**：补齐 `API_TO_TYPE`，并**刻意不动 `CATEGORIES`、也不动后端** —— 后端 `record_type` 词表与前端 tab 词表**本来就是两回事**，页面操控工具只负责把用户的话翻译成 tab key，不该去改数据模型。

修后 **18/26 落到真实 tab**（剩下 8 条 `other` 确实没有对应 tab，这是**真实结果，不是 bug**）。

**为什么难发现**：**因为它不报错。** 筛选返回空列表是完全合法的响应。而且这个缺陷会**伪装成"新功能不好用"** —— 如果先做页面操控再发现它，很容易误判成页面操控做坏了。

> 教训：**在旧缺陷上面盖新功能之前，先确认底座是好的。** 我是在做页面操控之前先修的这条，否则会花大量时间调试一个根本没接错的链路。

### 故事 15：加密做好了，就是没接上（健康数据明文落盘）

**现象**：做安全盘点时，直觉是"健康数据应该加密了吧"。

**查证**：`storage_tool.py` 里 Fernet **加密是完整实现的** —— `encrypt_data`（`:42`）、`decrypt_data`（`:51`）、`get_or_create_encryption_key`（`:30`）全在，写得没毛病。

**但**：全仓检索这两个方法的调用点，**除了 `page_control_tool.py:259` 的一句注释提到它，没有任何地方真的调用**。`save_health_record`（`:67`）把明文 `content` 直接 `INSERT` 进库。

**结论**：这不是"我们没做加密"，而是"**加密做好了，没接上**"。

**为什么这比"没做加密"更危险**：能力缺失会在评审时被问"加密呢？"；而**接线遗漏**不会 —— 因为代码看起来完备，评审看到 `Fernet` 三个字就点头了。前者是显性的洞，后者是隐性的洞，**且因为"代码里有"而更容易过审**。

> 教训：**"实现了"和"生效了"是两件事。** 验证一个安全机制，要查的是**调用链**，不是定义。这也是为什么我在架构文档里把"已实测验证的行为"单列成一张表 —— 只写"跑出来看到过"的。

### 故事 16：约束的粒度比删除的粒度粗，于是跨用户互相踩踏

**现象**：用户 B 索引一个 `source_id` 已被用户 A 用过的文档时，`/v2/rag/index` 直接 **500**：

```
duplicate key value violates unique constraint
"rag_chunks_source_type_source_id_chunk_index_embedding_mode_key"
```

**根因**：线上库上**同时存在两个唯一约束**：

| 约束 | 列 | 问题 |
|---|---|---|
| 旧的（遗留） | `(source_type, source_id, chunk_index, embedding_model)` | **不含 `user_id`** —— 把 `source_id` 当全局唯一 |
| 新的 | `(user_id, source_type, source_id, chunk_index, embedding_model)` | 正确 |

而 `rag.py` 的 `index_document` 是 `DELETE ... WHERE user_id=%s AND source_type=%s AND source_id=%s`（**按用户删**）再插入。**删的粒度比约束的粒度细** —— 于是"删不掉别人的行，又插不进自己的行"。

**修法**：新约束是旧约束的**严格超集**（多了 `user_id` 维度），所以删掉旧约束**不会放进任何"按租户语义本不该存在"的重复行**，只是恢复了多租户隔离。用 `IF EXISTS` 保证幂等。

**顺带踩到一个顺序陷阱**：必须**先删约束再删索引** —— 反过来先 `DROP INDEX` 会报 `cannot drop index ... because constraint ... requires it`（约束背后自动带索引，得从约束删）。

**为什么难发现**：**数据库不会告诉你"你删错了"**。它只会抛一个看起来跟删除逻辑无关的 duplicate key。而且这个 bug 只在"两个用户恰好用同一个 source_id"时触发 —— 单用户测试**永远复现不出来**。

> 教训：**约束的粒度必须和业务删除的粒度一致。** 这是多租户系统里一条容易被忽略的对称性要求。

### 故事 17：读代码读到了错的那份

**现象**：做架构梳理时，两个独立的调研线索给出的同一个文件**行号对不上**（`api.py:4976` vs `api.py:5223`）。

**查证**：仓库里**有两份 `api.py`**：

| 文件 | 行数 | 最后改动 | 状态 |
|---|---|---|---|
| `./api.py`（根目录） | 5323 | 2026-08-20 | **重构前快照**，还用 `@app.post` |
| `frontend/hostAgentAPI/api.py` | 5581 | 2026-10-02 | **真正生效的**，已重构成 `@router.post` |

**判定"哪份是真的"的三条独立证据**：
1. `Dockerfile` 的 `COPY frontend/hostAgentAPI ./` → 容器里是 `/app/api.py`，5581 行，与 frontend 版一致
2. `hostapi` 服务**没有任何卷挂载** → 完全靠镜像内容，根目录那份进不了容器
3. 全仓无 `import api`（除容器内的 `app.py:30`，而它解析到 `/app/api.py`）、无 Dockerfile COPY 根目录那份

**结论**：根目录 `api.py` 是**6 周前的死重**，零引用。

**同类第二处**：前端还有两个 900/700 行的 v1 页面（`HealthRecords.jsx` / `Medication.jsx`）同样零引用。它们的来历是——**2026-07 阶段 44 重写前端时新增了 4 个 `New*` 页面，路由改指新版，旧文件留在原地烂了三个月**。

`New*` 这个前缀就是化石证据：**本来是"临时占位名"，结果成了永久名**。而且这次迁移**不统一** —— `Dashboard` 是**原地升级**的（所以没有 `NewDashboard.jsx`，也就不存在孤儿），另外四个是**重写成新文件**的（于是旧版全成了孤儿）。**正是因为策略不统一，才留下一堆没人记得的旧文件。**

**为什么这是个好故事**：它说明**"读代码"本身也可能读到假的**。如果我没有交叉验证行号，整个架构文档会把一份过时的实现当成现状来写 —— 而且**每一处引用都会显得言之凿凿**。

**修法（含一个反面教训）**：三份死文件（`api.py` + 两个 v1 页面）已 `git rm`。但清理时我**差点误删 `pages/Header.jsx`** —— 我的孤儿扫描脚本按 `pages/Header"` 匹配，而它实际是被 `Home.jsx` / `ConversationPage.jsx` 以**相对路径** `from "./Header"` 引用的。**扫描脚本漏了相对路径这种写法，差点删掉一个活文件。**

> 教训有两条：① 判断"哪份文件是活的"，**别读代码，读构建配置**（Dockerfile 的 COPY、compose 的 volumes）—— 运行时事实永远优先于源码事实。② **删除前必须换一种方式复核**。删除后构建模块数不变（12066），这才是"确实没人用"的硬证据。

### 故事 18：同一个列，三个维度数字，五处 DDL

**现象**：`rag_chunks.embedding` 的维度，代码里写着 384，`.env` 里写着 1024，监控端点默认值写着 1536。

**查证**：这张表由**五处 `CREATE TABLE IF NOT EXISTS`** 各自声明：

| 出处 | 声明维度 |
|---|---|
| `v2/rag.py`（文档注释） | `vector(384)` |
| `knowledge_tool.py:202` | `vector(384)` |
| `health_records_api.py:764` 与 `:1153` | `vector(384)` |
| `database/migrations/..._init.sql:31` | **`vector(1024)`** |
| `database/postgres/init/02_...sql:142` | （随 env） |

而运行时维度是 `EMBEDDING_DIM` 环境变量驱动的：`rag.py:42` 默认 `384`，`.env:79` 是 `1024`，`monitoring_endpoints.py:398` 的默认值是 `"1536"`。

**危险点**：`CREATE TABLE IF NOT EXISTS` 意味着**谁先启动谁定表结构**，后跑的静默跳过。表一旦按某个维度建好，另一条路径的 `%s::vector(384)` 字面量转换就**直接报错**。所以"哪个维度生效"取决于**容器启动顺序** —— 典型的"本地能跑、换台机器就炸"。

**为什么难发现**：因为**在开发机上它永远是对的**（表早就建好了，`IF EXISTS` 一直跳过）。只有全新环境首次启动才会暴露，而那时你多半会怪"环境没配好"。

> 教训：**`CREATE TABLE IF NOT EXISTS` 是"多份真相"的温床。** 一个 schema 只该有一个权威定义（迁移脚本），运行时只负责读。

### 故事 19：指标端点在，但没人抓

**现象**：看板没数据。

**查证**：`/metrics` 端点**确实实现了**（rerank / CRAG / 限流等指标都在）。但 `docker-compose.yml` 里**没有 Prometheus 服务**，仓里也**没有 `prometheus.yml`** —— **没有任何东西去抓这个端点**。

**叠加**：这还叠上了故事 7 的问题 —— 那些指标在流式路径接上 RAG 之前**本来就恒为空**。于是"看板没数据"有**两个独立成因**，排查时都表现为同一句话。

**为什么值得讲**：这是"**看起来有、其实没有**"的典型 —— 端点存在、代码正确、指标定义完整，唯独缺了最后一根线。而**排查者的第一反应是"没流量"**，不会去问"有没有人在抓"。

> 教训：**可观测性是一条链，链上任一环断掉都等于没有。** 验证方式不是"端点返回 200"，而是"**数据真的出现在看板上**"。这和故事 15（加密没接上）是同一类病：**实现了 ≠ 生效了**。

## 4. 预设追问与回答

**Q：为什么用 MCP 而不是直接写函数调用？**
> 边界。MCP 让"工具"成为一个**可发现、可声明 schema、可跨进程**的东西。我的工具发现是**按 agent 隔离加载**的，没有全局工具表 —— 这保证了智能体的能力边界是显式的。代价是引入了 AST 静态扫描这种约束（见故事 8），但换来的隔离性我认为值得。

**Q：A2A 和 MCP 都在"调用"，区别是什么？**
> MCP 是**能力边界**（这个智能体能做什么），A2A 是**组织边界**（这个智能体能把活派给谁）。前者是动词的清单，后者是同事的清单。

**Q：AG-UI 有原生的 `STATE_DELTA`，你为什么自己加了个 `PAGE_UPDATE` 事件？**（**高概率被问，因为你说自己用了 AG-UI**）

> 先澄清一点：`PAGE_UPDATE` **不是绕过协议** —— AG-UI 本身留了自定义事件的扩展位，这是协议内的合法用法。真正的问题是「为什么不走官方那条现成的状态通道」。
>
> `STATE_DELTA` 是**状态同步**语义（「状态应该变成 X」，JSON Patch，幂等），`PAGE_UPDATE` 是**动作派发**语义（「执行 X，现在」，有调用、有返回值）。判断依据只有一条 —— **幂等性**：
>
> > 状态重放一次无害（「筛到检查」说两遍还是筛到检查）；动作重放一次会出事（弹窗重弹、toast 卡住）。
>
> 12 个动作按这条线切完是这样：
>
> | 通道 | 动作 | 为什么 |
> |---|---|---|
> | `STATE_DELTA`（幂等状态） | `navigateTo` → `route`<br>`setFilter` → `healthRecords.filter`<br>`setSearch` → `healthRecords.search`<br>`setView` → `medication.view` | 都是「我在哪、我在看什么」，收敛到声明值即可 |
> | `PAGE_UPDATE`（瞬态动作） | `setData` / `openRecord` / `fillForm` / `showAlert` / `refresh` / `askAgent` / `highlightAgent` | 有调用、有返回值、有副作用 |
>
> **留下不动的几个原因是硬的**：① `refresh` **根本没有状态可收敛**，硬做要引入一个假计数器；② `showAlert` 是瞬态事件，做成状态意味着「toast 一直亮着直到有人关掉」，重连即卡住；③ `setData` 是**追加**语义，后端并不持有卡片全量，做成状态就得让后端先读一遍现有列表；④ 状态收敛**会重放副作用** —— 我在 `ComponentRegistry.jsx` 里已经踩过这个坑（注释里写着「重复的 `openRecord` 会在用户关掉弹窗后又把它弹开」），在动作通道里是要**对抗**的行为，而它在 `STATE_DELTA` 里是**设计特性**。
>
> **我做了这个混合，不是"如果重做我会"。** 关键洞察是：**声明式子集天然幂等，所以状态收敛语义对它们是安全的；只有瞬态动作才会被重放咬到。** 落地时有三点值得说：
>
> 1. **用 `add` 而不是 `replace`** —— RFC 6902 规定 `add` 到已存在的对象成员即等于替换，所以后端**不需要知道前端当前状态**，无脑 add 就能表达"把 `/a/b` 设成 v"。工具只声明自己改了什么，不必持有全量 state。
> 2. **迁移没有 flag day** —— 过渡期两条通道都发，且页面上的用户交互（点 tab、打字）也写**同一个** `pageStateStore`。两条路收敛到同一个值、幂等无害，所以任何一端没重建成功功能都不会坏。
> 3. **顺手消掉了一个依赖** —— `filter_health_records` 原本发 `[navigateTo, setFilter]` 两个动作，靠 `ComponentRegistry` 的待执行队列兜住"目标页还没挂载"。改成一次 state patch 后，页面挂载时直接读到 store 里的当前值，**这条路径不再需要队列**。
>
> **实测**（进了常驻回归 `tests/e2e/agui_smoke.py` 用例 E）：问「帮我打开健康档案页，只看检查的」→ `STATE_DELTA: 1`，delta 是 `[{add,/route,/v2/health-records}, {add,/healthRecords/filter,exam}]`；同一次调用 `PAGE_UPDATE: 2` 照旧发出（双轨兜底）。另外我把 patch 的**幂等性**单独测了 —— 同一条 patch 连放三次结果一致，**这是状态通道能成立的前提**，不幂等的话网络重投递就会把页面推向错误状态。
>
> **代价我认**：`PAGE_UPDATE` 那半仍然没有标准背书，别的 AG-UI 客户端还是驱动不了我的界面；而且契约耦合**变多了一处** —— `shared_page_control.py` 里 `page_state` 的键名必须和 `pageStateStore.js` 的 schema 一致，拼错一个字母 patch 会安静地写进没人读的键（这条我记在架构文档 §11 第 16 条）。

**Q：为什么不本地部署模型？**
> 明确的设计约束。本地模型拖慢镜像、吃内存、增加部署复杂度，而这套栈本来就是 API 驱动的（DeepSeek + DashScope）。需要重排就走 DashScope 的 HTTP API。**这是个成本/复杂度权衡，不是能力妥协。**

**Q：12 个月一个人做，怎么保证质量？**
> 三个层次：① 15 个 `verify_stage*.py` 阶段验证脚本 + 1 个**阻断式** CI 守卫；② 关键路径有**实测证据**而不是"看起来对"（架构文档 §12 列了表）；③ 代码注释写**决策原因**。不过要诚实说：**`api.py` 5581 行是明显的结构债**，一个人做最容易牺牲的就是模块化。

**Q：这套东西的短板在哪？**（**必答，主动说**）
> 按严重程度，**安全相关的排前面**：
> 1. **健康数据明文落盘** —— Fernet 加解密**实现了但零调用**（故事 15）。这不是"没做加密"而是"做好了没接上"，比前者更隐蔽。
> 2. **密码用 `sha256+salt` 而不是 bcrypt/argon2** —— 真实的安全缺陷，不是风格问题。
> 3. **跨会话长期记忆基本空转** —— 唯一写入点 `aggregate_node` 只在 `host_graph` 里，而流式路径不过 host_graph。**会话内多轮是好的，跨会话没接。**
> 4. **`rag_chunks` 的 schema 有五份定义、三个维度数字**（故事 18）—— 换机器可能直接炸。
> 5. **`api.py` 单文件 5581 行** —— 该拆没拆。（根目录那份 6 周前的死副本和两个 v1 孤儿页面已经删掉了，见故事 17）
> 6. **两个聊天入口能力不一致** —— 浮窗能操控页面、全页聊天不能。同一件事两套实现。

> 这一串里有个共同点值得点出来：**第 1、3、4 条都是"实现了但没接上"**，不是"不会做"。这是我做这个项目最大的收获 —— **一个系统的真实能力，取决于接线，不取决于代码库里有什么。**

**Q：如果重做，你会改什么？**
> 按优先级：
> 1. **把"两条并行路径"合并成一条**（故事 7 的根因）—— 并行路径的债是**复利**的：每加一个能力，你都要问"另一条接了吗"。故事 15/19 都是这个模式的下游产物。
> 2. **给每个 schema 定一个权威来源**（故事 18）—— 消灭"多份真相"。
> 3. 然后把 `hostapi` 拆开 —— 它现在是 A2A Host + 编排器 + AG-UI 转译层 + REST API 四合一。
> 4. 加一条 CI 检查：**关键安全机制必须有调用链证据**（比如"Fernet 被调用了"、"metrics 被抓取了"），而不只是"定义存在"。

## 6. 这个项目的边界（主动划清）

**做到了**：四协议分层、多跳 RAG + KG + 重排（MRR 有实测）、CRAG、AI 页面操控、HITL 草稿确认、Ed25519 DID、RBAC、零停机部署、日志聚合看板。

**没做到 / 没验证**：
- RAG 评测样本只有 20 来条，**MRR 1.0 说明方向对，不代表生产效果**
- 没有真实用户量，**性能数字都是单机压测**，不是生产数据
- 密码哈希算法是**已知的安全缺陷**
- 阿里云 OCR 是**占位实现**
- 没有移动端原生应用（有小程序）

> **主动划边界是加分项。** 面试官见过的"什么都做了、什么都很好"的项目太多了；一个能准确说出"我哪没做好、为什么"的候选人，可信度高得多。
